Summary: Give the module's macro a /_name scope parameter and move its logic under that scope.

This step applies after the module's logic lives in its own TLV macro
(`\TLV <module_name>(/_top)`). Every converted module follows the TLV macro
block convention: the caller names the scope, the macro opens it, and
everything the macro defines lives under it. Apply this to every module,
including ones instantiated only once; the original code drew a module
boundary here and the scope preserves that structure. If the macro already
takes /_name and its body is already under that scope, report NO_CHANGE.

The convention, as documented for the `wire` macro:

   // wire(
   //    /_top:  Top-level scope.
   //    /_name: A unique level of hierarchy for the instance.
   //    $_in:   An input pipesignal in /_top scope, optionally with a bit range.
   //    $_out:  An output signal in /_name with bit range (unless boolean).
   // Connects an input signal to an output signal.
   // Should be called within a pipestage.
   \TLV wire(/_top, /_name, $_in, $_out)
      /_name
         $_out = /_top$_in;

   // A sample call in context.
   \TLV
      |pipe
         @1
            $in_byte[7:0] = ...;
            m5+wire(|pipe, /connection1, $in_byte1, $out[7:0])
            $stuff = /connection1$out

Macro parameters are dumb text substitution with no language-level
namespacing, so the scope is what keeps two instantiations of the same
macro from colliding: each call passes a different name.

Transform:

1. Add /_name to the macro's parameter list, after /_top, following the
   underscore-prefixed parameter naming convention:
   `\TLV <module_name>(/_top, /_name)`.
2. Make `/_name` the first line of the macro body and indent everything
   that was in the body one level (3 spaces) beneath it. Pipelines,
   stages, and logic move under the scope unchanged. No logic stays
   outside the scope.
3. References the macro makes to signals in the enclosing context now
   reach out through /_top (`$sig = /_top$sig;`). References among
   signals the macro itself defines need no edits; they move with the
   scope.
4. The instantiation site passes the name, conventionally the module
   name: `m5+<module_name>(/_top, /<module_name>)`.
5. Every reference from outside the macro to a signal the macro defines
   (the including context, and the module wrapper's interface
   connections) reaches into the scope, e.g. `|default$rgnt` becomes
   `/<module_name>|default$rgnt`.

Introducing the scope renames every signal SandPiper generates from the
macro, so the FEV match lines must follow: in each fev*.eqy match
section, add the scope to the path of every gate-side name (TL-Verilog
syntax) for a signal now under the scope (e.g. `|default<>0$rgnt` becomes
`/rf_ram_if|default<>0$rgnt`). The gold side (instance-prefixed names
from the flattened original Verilog) does not change; do not touch it.

A mechanical cross-check runs before FEV: it enumerates both sides'
signals and rejects match lines that name signals that do not exist, or
gold state left unmatched. If it fails, no FEV run is spent; fix the
listed disagreements. You can run it yourself as
`./scripts/gen_match_lines.py --check <fev_full*.eqy>`.

Report in tracker.md which scope name was introduced and how many match
lines were updated.
